Summary

  • General use is now ranked on a new General score (GS), not the AA Intelligence Index. About half of the Index is agentic and coding work [3], which double-counted coding. GS keeps only the Index's chat-type evals, scores Omniscience by penalising wrong answers rather than rewarding refusals, and halves CritPt (how to read this). This reshuffles most General tables.
  • qwen3.6:27b-q4_K_M is now the top dense general pick (GS 32.0, ≈ o3) wherever it fits and is fast enough. qwen3.8:27b-q4_K_M (GS 27.1) stays in General only on 32-36 GB Macs, but still leads coding among independently scored 27B models [4].
  • Mac 128 GB gets two big changes. qwen3.8-flash-next:125b-a6b-nvfp4 is now #1 for coding too (TB 86.1) because the MLX bugs that kept it out are fixed in Ollama 0.40.4 [2]. nemotron-3.5-super is new at #2 general (GS 37.2) and #4 coding (vendor TB 66.7).
  • Ollama 0.40.4 fixes two MLX bugs: the per-tool-call memory leak (#18620) and the "Maximum threads" crash (#18846). The tables still list GGUF tags; the new MLX swap column in Mac General tables names the MLX build to use instead (tag choice).
  • granite4.2:3b now leads General on 8 GB Macs, the base M1 16 GB and the Latitude (GS 18.9). It scores just below qwen3.5:4b-q4_K_M (GS 19.9) but is faster, so it ranks first. The two suit different jobs [4]:
    • Granite is the safer pick for factual questions. It answers fewer questions correctly (9.2% vs 15.1% on AA-Omniscience), but it gives a wrong answer on about 24% of questions against Qwen's 74%; it says "I don't know" instead.
    • Qwen is the better pick for long documents and reasoning (AA-LCR 63.0% vs 24.3%).
  • For coding, ornith-1.5:35b still ranks #1 on Macs with 48-96 GB and on the Pro Max 16 Plus, on its vendor's own score only (TB 67.8) [5]. Coding ranks are unchanged outside Mac 128 GB.
  • Below 32 GB, local agentic coding is weak. The best picks score near Gemini 2.5 Pro or Claude 4.5 Haiku. On base M1 Macs (8 or 16 GB), no coding candidate passes the filters, so use a cloud model for coding there.
  • One config change matters more than model choice: context length. Ollama defaults to 4k context below 24 GiB of GPU memory, OpenCode needs 64k or more, and Ollama's OpenAI-compatible /v1 endpoint, which OpenCode uses, can't change it per request [6][7][8]. Every pick below needs the context fix.

How to read this

  • Hardware tier: a group of machines that can run the same models. Each tier heading lists the machines in it.
  • Use cases: General use is chat, writing and reasoning. Agentic coding is OpenCode driving tools on its own.
  • Scores come from Artificial Analysis (AA) [4], which tests open and paid models with one harness:
    • General use: General score (GS), built from AA's per-eval scores. It's the weighted mean of the Intelligence Index v4.3.2's non-agentic, non-coding evals [3]: HLE 10, CritPt 5, AA-Omniscience penalty score 15, AA-LCR 5. GDP.pdf (weight 10 in the Index) isn't in AA's leaderboard data, so it's left out. A model missing any input has no GS and isn't ranked for General. Paid equivalents use the same score.
    • Omniscience penalty score: +1 for each correct answer, 0 for "I don't know", −0.5 for each wrong answer, rescaled to 0-100. The −0.5 penalty is the one the AA-Omniscience paper suggests [9]; OpenAI's SimpleQA paper also recommends penalising wrong answers this way [10]. The wrong-answer share comes from AA's data as accuracy minus the Omniscience Index.
    • Why not AA's own split (accuracy 10 + non-hallucination 5): non-hallucination counts only how often a model declines instead of answering wrongly, and ignores correct answers, so a model that refuses every question scores 100% [9]. That let small models that refuse a lot top the small tiers.
    • Why CritPt is halved: it's 70 research-level physics problems, and most local models score near zero [11]; at full weight it mostly adds noise. AA also expects CritPt scores to be revised [11].
    • Why not the full Index: about half of it is agentic and coding evals [3], which the Agentic coding table already covers. GS is on a different scale from the Index, so don't compare the two numbers.
    • Agentic coding: AA Terminal-Bench 2.1. In AA's data, recent models such as Qwen3.8 have no Terminal-Bench Hard score, so 2.1 is the column that covers both sides [4].
    • Vendor-reported scores are used only when AA has none, and are flagged (vendor).
  • Equivalent paid model: the paid model whose score on the same benchmark is closest.
  • Est. tok/s: estimated output speed, computed as 0.6 × memory bandwidth ÷ GB of weights read per token. It's a rough estimate, never measured (unsourced). The range runs from the slowest to the fastest machine in the tier.
  • Ranking rules:
    • Every pick must support tool calls in Ollama, fit on every machine in the tier with 64k context, and reach about 15 tok/s on at least one of them.
    • Tool support means Ollama reports it: either the model has the tools badge, or its model file carries a chat template that handles tools, which Ollama 0.40 also counts as tool support and runs through llama.cpp's own template code [12]. Ornith 1.5 and Granite 4.2 qualify the second way.
    • Coding picks need TB ≥ 20.
    • ⚠ marks a coding pick with an open tool-call bug report. The report says tool calls break or go missing in normal use through Ollama's chat API, in the model's Ollama parser (the code that turns the model's output into tool calls). Every model that uses that parser gets the flag. A model without a parser is flagged only when a report names it. Reports that need an unusual request don't count.
    • The flag doesn't change the score or the rank. Before adopting a flagged pick, run a short OpenCode session that reads, edits and runs code, and watch for failed or missing tool calls.
    • A model is excluded from coding only when an Ollama maintainer confirms such a bug: they reproduce or acknowledge it, or link their own fix. As of 2026-10-15 none of the open reports is confirmed.
    • When two models are within 3 points, the one that's faster on the tier's slowest machine ranks higher.
    • Each tier keeps at least one pick that's fast on every machine in it, if one exists.

How the tiers are drawn

Each tier heading below lists the machines it covers.

  • Macs use unified memory. A model must fit the smallest machine in its tier.
    • Up to 36 GB: a model's weights should take no more than about 60% of RAM, which leaves room for macOS, the GPU memory cap and 64k of context (estimate).
    • 48 GB and up: the weights plus the memory for 64k of context must fit in RAM minus 16 GB, which keeps 16 GB for macOS and apps (estimate). Context memory is computed from each model's file at Ollama's default precision; hybrid models that keep context in only some layers need much less. Models above macOS's default GPU memory cap need the cap raised (section 3).
  • 18 GB and 24 GB Macs share a tier with 16 GB Macs. Under the 60% fit rule, no better model fits.
  • Base M1 Macs (8 and 16 GB) have their own tiers. Their bandwidth is so low that they get different picks from other Macs with the same memory.
  • The Latitude 7350, Pro 14 Premium and Pro Max 16 have no discrete GPU, or only a 6-8 GB one. Their RAM bandwidth is about 90-137 GB/s, versus 150-614 on Pro/Max Macs.
    • Only MoE models reach usable speed on them. MoE (mixture of experts) means only a few billion parameters are read for each token.
    • Bandwidth figures: Apple specs [13]; Dell RAM speeds [14], with bandwidth computed as MT/s × 16 bytes (estimate); NVIDIA [15]. The base M1's ~67 GB/s isn't published by Apple; it's derived from Apple's "M2 has 50% more" (unsourced).
  • The Pro Max 16 Plus tiers depend on the GPU.
    • A model runs entirely in VRAM if it's no bigger than VRAM minus 3 GB. Only the 24 GB RTX PRO 5000 can hold a 27B dense model that way.
    • Otherwise Ollama splits the model between the GPU and system RAM, and RAM speed sets the pace.

Config changes

1. Ollama server settings (all machines)

Variable Value Why
OLLAMA_CONTEXT_LENGTH 65536 Fallback for any model without a Modelfile. Default is 4k below 24 GiB of GPU memory [6].
OLLAMA_FLASH_ATTENTION 1 Already automatic on supported backends; setting it removes doubt [32]
OLLAMA_KEEP_ALIVE 30m Default 5m unloads the model during pauses in an agent session [32]
OLLAMA_NUM_PARALLEL 1 (default) Each parallel slot multiplies KV-cache memory [32]
OLLAMA_KV_CACHE_TYPE unset (f16), or q8_0 if memory is tight q8_0 roughly halves context memory; per the FAQ, "this usually has no noticeable impact" [32]. Open #17347 reports Qwen 3.5/3.6 stopping before tool calls with q8_0 on AMD ROCm

How to set these variables:

  • macOS: run launchctl setenv OLLAMA_CONTEXT_LENGTH 65536 (and likewise for the others), then restart the Ollama app [32]. Also set the context length with the app's Settings slider [6].
  • Windows:
    1. Quit Ollama from the tray.
    2. Open Settings → "Edit environment variables for your account" and add the variables.
    3. Start Ollama again [32].
  • Windows GPU extras:
    • NVIDIA driver must be 551.61 or newer [33].
    • If the Intel iGPU causes instability on a Pro Max, keep Vulkan on and set GGML_VK_VISIBLE_DEVICES to the NVIDIA GPU's index. OLLAMA_VULKAN=0 turns Vulkan off completely and is the general fallback [21].

2. Per-model context fix (required)

OpenCode talks to Ollama's /v1 endpoint, which can't set the context size per request. So bake the context size into a model of your own [8]:

Machines num_ctx
Macs up to 36 GB; all Dells except the 24 GB GPU 65536, the minimum Ollama recommends for OpenCode [7]
Macs 48 GB+; Pro Max 16 Plus with 24 GB GPU 131072 
# Modelfile (example: Mac 48-96 GB)
FROM qwen3.8:27b-q4_K_M
PARAMETER num_ctx 131072

ollama create oc-qwen3.8-27b -f Modelfile
ollama ps        # CONTEXT should read 131072; PROCESSOR 100% GPU

Use the full tag in FROM. On a Mac, FROM qwen3.8:27b resolves to the MLX build; name the GGUF tag or the -nvfp4 tag explicitly so you know which one you get (tag choice).

Sampling settings: most Ollama tags already carry the vendor's recommended values. For example, qwen3.8 ships with temperature 1, top_p 0.95 and top_k 20, matching its model card [25].

Exception: qwen3.6:35b-a3b-q4_K_M. It ships presence_penalty 1.5, but Qwen recommends 0.0 in thinking mode, which it runs by default (#17197, [34]). The qwen3.6:27b-q4_K_M tag already ships 0. Add this to the 35B's Modelfile:

PARAMETER presence_penalty 0

Ornith 1.5 tags ship no sampling settings, so Ollama's defaults apply. The vendor ran its benchmarks at temperature 1.0 and top_p 0.95-1.0 [5]; add those to the Modelfile to match.

For coding with either Qwen 3.6 pick, Qwen's thinking-mode value for precise coding is PARAMETER temperature 0.6 [34].

Qwen 3.5 coding picks (qwen3.5:4b-q4_K_M, qwen3.5:9b-q4_K_M) ship temperature 1 and presence_penalty 1.5. Qwen's card gives temperature 0.6 and presence_penalty 0 for precise coding in thinking mode [35], so add both to their Modelfiles when used for coding.

3. Mac GPU memory limit

macOS caps how much unified memory the GPU can use. The default cap isn't published by Apple; it's commonly reported as about 2/3 of RAM on Macs up to 36 GB and about 3/4 above that (unsourced). A model that doesn't fit under the cap still runs, but part of it runs on the CPU (unsourced). ollama ps shows that split [32], and Ollama advises avoiding CPU offload for best performance [6].

Check first. Load the model, then run ollama ps. If PROCESSOR reads 100% GPU, the model is entirely on the GPU, so leave the cap alone. A split such as 48%/52% CPU/GPU means part of it spilled [32].

Tier When to raise the cap Example value
Mac 32-36 GB If ollama ps shows less than 100% GPU with a pick of 16 GB or more (16-19 GB + context is close to the default cap) 26000 on 32 GB · 29000 on 36 GB
Mac 128 GB Required for qwen3.8-flash-next (105 GB), the #1 pick, and nemotron-3.5-super (90 GB) 114000
All other tiers Not needed for the picks in this report —

The value is in MB. It must be larger than the model and smaller than total RAM [36]. The example values leave about 7-17 GB for macOS (estimate).

Until the next reboot:

sudo sysctl -w iogpu.wired_limit_mb=26000

Permanent: add the same setting to /etc/sysctl.conf, which macOS applies at boot (unsourced):

echo "iogpu.wired_limit_mb=26000" | sudo tee -a /etc/sysctl.conf
  • Risk: setting it too high starves macOS of memory, which causes swapping or freezes (unsourced). Raise it in small steps and re-check ollama ps.
  • To undo: set it to 0 (macOS default) and remove the line from /etc/sysctl.conf.

4. Tag choice

  • Ollama 0.40 runs supported models on MLX by default on Apple silicon, starting with Qwen 3.8, Qwen 3.6, Qwen 3.5 and Gemma 4 [37]. MLX is Apple's machine-learning framework [18].
  • Short tags now hold two builds. qwen3.8:27b, qwen3.5:27b, qwen3.5:9b, qwen3.5:4b, qwen3.5:2b and qwen3.5:0.8b each list an MLX build and a GGUF build [30]. On Apple silicon Ollama picks MLX first; elsewhere it picks GGUF first [38].
  • The tables list explicit GGUF tags (-q4_K_M, -q8_0, -it-qat, or a tag with only a GGUF build). They load the same build on Mac and Windows.
  • Two MLX bugs are fixed in Ollama 0.40.4 [2]:
    • #18620, the MLX runner leaking memory on every request that ends in a tool call, closed by an Ollama maintainer with PR 18955.
    • #18846, the "Maximum threads" crash on qwen3.6:35b-mlx and qwen3.8:27b-mlx, closed with PR 18956 (an MLX version bump).
    • Nobody has yet reported on how the fixed builds behave in long agent sessions.
  • Macs can now use the MLX build for either use case. Take the MLX swap tag from the General table (an -nvfp4 tag), or the short tag. NVFP4 generates about 20% faster than q4_K_M, per Ollama [16]. Update to 0.40.4 or later first.
  • One MLX report is still open: #18754 (GPU only 50-70% busy on an M4 Pro). If MLX isn't faster on your Mac, stay on the GGUF tag.
  • The tables still list GGUF tags so that ranks, sizes and speed estimates use one format across Mac and Windows.
  • To check which engine loaded, run ollama ps: its RUNNER column reads mlx for the MLX build [39].
  • Muse Glimmer: use muse-glimmer:30b-q4_K_M. Its 30b-mlx tag still has open bugs (#17656, #18269), and it's unclear whether they also affect 30b-nvfp4.

5. OpenCode 2.x (~/.config/opencode/opencode.jsonc)

Ollama is discovered automatically. OpenCode 2 probes http://127.0.0.1:11434, lists every Ollama model that can chat, and reads context, vision and tool-use capabilities from Ollama, with no provider config needed [40]. Select a model as ollama/<tag>.

Still override the context limit. Discovery reads each model's maximum context from Ollama, not your num_ctx [41], and requests go through Ollama's /v1 endpoint, which has no way to set the context size [42][8]. So keep the Modelfile fix from section 2, and tell OpenCode the same limit. A limit set in config overrides the discovered value. Example for a Mac with 48-96 GB, matching the Modelfile above [42][40]:

{
  "$schema": "https://opencode.ai/config.json",
  "model": "ollama/oc-qwen3.8-27b",
  "providers": {
    "ollama": {
      "models": {
        "oc-qwen3.8-27b": {
          "name": "Qwen3.8 27B (local, 128k)",
          "capabilities": { "tools": true, "input": ["text", "image"], "output": ["text"] },
          "limit": { "context": 131072, "output": 16384 },
        },
      },
    },
  },
  "compaction": { "auto": true },
}
  • limit.context must equal the model's num_ctx. It tells OpenCode when to compact; it doesn't change Ollama. Automatic compaction is on by default and keeps 10% of the limit free [43].
  • Malformed tool calls now fail visibly (2.0.25). OpenCode no longer repairs bad tool-call JSON; it sends the model a tool error so it can retry [44]. With the parser bugs above, expect the odd retried tool call rather than a silent fix.
  • Key names changed from 1.x: 2.x uses providers, package, settings and capabilities.tools [42][40], where 1.x used provider, npm, options and tool_call [45]. small_model isn't in the 2.x docs; title and summary work is done by hidden built-in agents [46].
  • The config schema now describes 2.x. The schema at opencode.ai/config.json has the providers key and marks 1.x keys such as provider and small_model as deprecated [45].
  • Remote Ollama: set providers.ollama.settings.baseURL to its /v1 URL [42].
  • Keep MCP servers to a minimum. MCP tools consume model context [47]. OpenCode's own system prompt plus tools already use about 7-10k tokens (estimate).
  • Prefer the config above to ollama launch opencode. Ollama's OpenCode page shows only 1.x setup (the Windows install is the 1.x package opencode-ai; the manual config uses provider and npm), and it doesn't say which OpenCode version ollama launch targets [7].
