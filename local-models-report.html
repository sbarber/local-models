Summary

  • Mac tables list the best build of each model, MLX or GGUF. On Apple silicon Ollama runs two kinds of build: GGUF (through llama.cpp, the same files as on Windows) and MLX (Apple's machine-learning framework) [3][4]. Each Mac pick uses whichever build fits the tier and is estimated faster; when the two are within 10%, the MLX build is listed, because Ollama reports its NVFP4 builds about 20% faster than q4_K_M [5] (tag choice).
  • New this update: Flint, a coding model for Macs only. Recursive's flint (40B MoE, about 2.5B active) enters the coding tables at #5 on Macs with 32-96 GB, on its vendor's score (TB 54.9) [6]. It's the fastest coding pick in both tiers. Its only build that runs on the current Ollama is the MLX flint:40b-a2b-qat-int4: the GGUF builds need Ollama 0.40.9, which is still a release candidate, and Ollama says support beyond macOS comes in a later release [2][7]. So Flint isn't ranked for Windows, and it has no General score. It isn't flagged, but an open report says it re-sends integer tool arguments as text after the first tool call (#19191); test it before relying on it.
  • ornith-1.5:122b-nvfp4 is new at #2 for coding on Mac 128 GB (TB 81.2, vendor) [8]. Its MLX build uses Ollama's ornith parser, which has an open bug report, so it carries the ⚠; its GGUF build 122b-q4_K_M has no parser and no flag.
  • 24 of the 40 picks in the Mac tiers from 16-24 GB up are MLX builds. GGUF is listed where its file is clearly smaller (qwen3.5:4b-q4_K_M), where a model has no MLX build (Granite, Ornith 9B and 35B, qwen3.5:122b-a10b), for qwen3.6:27b-q4_K_M on 32-36 GB Macs, whose MLX build would reach 15 tok/s on none of the machines there, and for nemotron-3.5-super in coding (next bullet).
  • The smallest dense build, qwen3.5:27b-int4 (MLX, 16 GB), ranks high on Macs. It's #1 for General on 32-36 GB Macs and #2 on 48-96 GB (GS 29.0): it's within 3 points of the GS 32.0 picks and slightly faster than their 17-19 GB builds.
  • nemotron-3.5-super uses two builds on Mac 128 GB. General uses the MLX 120b-a12b-nvfp4 (80 GB): it's faster than the GGUF build and fits under macOS's default GPU memory cap (estimate; section 3). Coding uses 120b-a12b-q4_K_M, because NVIDIA reports the NVFP4 build at TB 60.8 against 66.7 for the full model [9].
  • Coding picks count the memory for 64k of context, OpenCode's minimum. On Macs up to 36 GB they assume you raise macOS's GPU memory limit to about 80% of RAM (section 3). With that, the Ornith 35B MoE models fit the 32-36 GB coding table. On Windows 32 GB, qwen3.5:35b-a3b (General) and ornith:35b (coding) aren't listed: their context doesn't fit beside their weights. A few General picks on small machines need a context below 64k (section 2).
  • Use Ollama 0.40.8 or later. It adds Flint, whose MLX build needs 0.40.8; 0.40.5 added Nemotron 3.5 support, and 0.40.4 fixed two MLX bugs that affected agent use [2][7].
  • nemotron-3.5-lightning:30b-a3b-nvfp4 now ranks #4 for General on 32-36 GB Macs. Ollama has rebuilt this MLX tag (library update 2026-10-16), and it's now smaller: 19.1 GB by its manifest [7][10]. That fits under 60% of a 32 GB Mac, and as a MoE it's much faster there than the dense picks.
  • General use is ranked on the General score (GS), not the AA Intelligence Index. About half of the Index is agentic and coding work [11], which would double-count coding. GS keeps only the Index's chat-type evals, scores Omniscience by penalising wrong answers rather than rewarding refusals, and halves CritPt (how to read this).
  • granite4.2:3b-q4_K_M leads General on 8 GB Macs, the base M1 16 GB and the Latitude (GS 18.9). It scores just below qwen3.5:4b-q4_K_M (GS 19.9) but is faster, so it ranks first. The two suit different jobs [12]:
    • Granite is the safer pick for factual questions. It answers fewer questions correctly (9.2% vs 15.1% on AA-Omniscience), but it gives a wrong answer on about 24% of questions against Qwen's 73%; it says "I don't know" instead.
    • Qwen is the better pick for long documents and reasoning (AA-LCR 63.0% vs 24.3%).
  • For coding, ornith-1.5:35b ranks #1 on Macs with 32-96 GB and on the Pro Max 16 Plus, on its vendor's own score only (TB 67.8) [13]. On Mac 128 GB, qwen3.8-flash-next:125b-a6b-nvfp4 leads both use cases (GS 40.2, TB 86.1).
  • Below 32 GB, local agentic coding is weak. The best picks score near Gemini 2.5 Pro or Claude 4.5 Haiku. On base M1 Macs (8 or 16 GB), no coding candidate passes the filters, so use a cloud model for coding there.
  • One config change matters more than model choice: context length. Ollama defaults to 4k context below 24 GiB of GPU memory, OpenCode needs 64k or more, and Ollama's OpenAI-compatible /v1 endpoint, which OpenCode uses, can't change it per request [14][15][16]. Every pick below needs the context fix, MLX builds included.

How to read this

  • Hardware tier: a group of machines that can run the same models. Each tier heading lists the machines in it.
  • Use cases: General use is chat, writing and reasoning. Agentic coding is OpenCode driving tools on its own.
  • Scores come from Artificial Analysis (AA) [12], which tests open and paid models with one harness:
    • General use: General score (GS), built from AA's per-eval scores. It's the weighted mean of the Intelligence Index v4.3.2's non-agentic, non-coding evals [11]: HLE 10, CritPt 5, AA-Omniscience penalty score 15, AA-LCR 5. GDP.pdf (weight 10 in the Index) isn't in AA's leaderboard data, so it's left out. A model missing any input has no GS and isn't ranked for General. Paid equivalents use the same score.
    • Omniscience penalty score: +1 for each correct answer, 0 for "I don't know", −0.5 for each wrong answer, rescaled to 0-100. The −0.5 penalty is the one the AA-Omniscience paper suggests [17]; OpenAI's SimpleQA paper also recommends penalising wrong answers this way [18]. The wrong-answer share comes from AA's data as accuracy minus the Omniscience Index.
    • Why not AA's own split (accuracy 10 + non-hallucination 5): non-hallucination counts only how often a model declines instead of answering wrongly, and ignores correct answers, so a model that refuses every question scores 100% [17]. That let small models that refuse a lot top the small tiers.
    • Why CritPt is halved: it's 70 research-level physics problems, and most local models score near zero [19]; at full weight it mostly adds noise. AA also expects CritPt scores to be revised [19].
    • Why not the full Index: about half of it is agentic and coding evals [11], which the Agentic coding table already covers. GS is on a different scale from the Index, so don't compare the two numbers.
    • Agentic coding: AA Terminal-Bench 2.1. In AA's data, recent models such as Qwen3.8 have no Terminal-Bench Hard score, so 2.1 is the column that covers both sides [12]. AA has since added Terminal-Bench 4.0, and of the models here only qwen3.8-flash-next (25.3) and qwen3.8:27b (5.1) score above 5 on it; the rest score 0-5 or aren't scored, so it can't separate them [12].
    • Vendor-reported scores are used only when AA has none, and are flagged (vendor).
    • Effort rows: where AA scores a model at several reasoning settings, the report uses the one Ollama runs by default: Medium for Qwen 3.8, and thinking on for Gemma 4 and the other thinking models [20].
  • Equivalent paid model: a paid model whose score on the same benchmark is close. Among paid models within 3 points, current models come before deprecated ones, then the closest score.
  • Est. tok/s: estimated output speed, computed as 0.6 × memory bandwidth ÷ GB of weights read per token. It's a rough estimate, never measured (unsourced). The range runs from the slowest to the fastest machine in the tier. MLX and GGUF builds use the same formula; Ollama's reported MLX speed-up isn't added.
  • Builds (Macs only): each model is ranked once, as its best build for the tier. Its score belongs to the model, so the build only changes fit and speed. The build that fits and is estimated fastest is listed, but an MLX build within 10% of it is listed instead, unless that would cost the pick its 15 tok/s on any machine. Ranking uses the fastest build's speed, so the choice of build never moves a pick down. The Model reference lists the other build of each model.
  • Ranking rules:
    • Every pick must support tool calls in Ollama, fit on every machine in the tier, and reach about 15 tok/s on at least one of them.
    • Context memory: coding picks must fit their weights plus 64k of context, OpenCode's minimum [15]. General picks on Macs up to 36 GB and on the Dells are fit on their weights and must leave room for at least Ollama's default 4k context [14]; where 64k won't fit, section 2 gives the largest context that does.
    • Tool support means Ollama reports it: either the model has the tools badge, or its model file carries a chat template that handles tools, which Ollama 0.40 also counts as tool support and runs through llama.cpp's own template code [21][22]. Ornith 1.5 and Granite 4.2 qualify the second way. MLX builds get tool support from their Ollama tool-call parser, the same one as their GGUF build [21][7].
    • Coding picks need TB ≥ 20.
    • ⚠ marks a coding pick with an open tool-call bug report. The report says tool calls break or go missing in normal use through Ollama's chat API, in the model's Ollama parser (the code that turns the model's output into tool calls). Every model that uses that parser gets the flag. A model without a parser is flagged only when a report names it. Reports that need an unusual request don't count.
    • The flag doesn't change the score or the rank. Before adopting a flagged pick, run a short OpenCode session that reads, edits and runs code, and watch for failed or missing tool calls.
    • A model is excluded from coding only when an Ollama maintainer confirms such a bug: they reproduce or acknowledge it, or link their own fix. As of 2026-10-22 no Ollama member or collaborator has confirmed any open report against a pick's parser. One Gemma 4 report was reproduced by an Ollama contributor (see the Mac 32-36 GB notes).
    • When two models are within 3 points, the one that's faster on the tier's slowest machine ranks higher.
    • Each tier keeps at least one pick that's fast on every machine in it, if one exists.

How the tiers are drawn

Each tier heading below lists the machines it covers.

  • Macs use unified memory. A model must fit the smallest machine in its tier.
    • Up to 36 GB: for General use, a model's weights should take no more than about 60% of RAM (estimate). For coding, the weights plus the memory for 64k of context must fit in 80% of RAM, which assumes you raise macOS's GPU memory limit to about that (section 3); the rest is left for macOS and apps (estimate).
    • 48 GB and up: for both use cases, the weights plus the memory for 64k of context must fit in RAM minus 16 GB, which keeps 16 GB for macOS and apps (estimate). Context memory is computed from each model's file at Ollama's default precision; hybrid models that keep context in only some layers need much less. Models above macOS's default GPU memory cap need the cap raised (section 3).
  • 18 GB and 24 GB Macs share a tier with 16 GB Macs. Under the 60% fit rule, no better General model fits. For coding, gemma4:26b-nvfp4 (TB 39.0) also fits 24 GB Macs with the raised GPU limit, but not the 16 and 18 GB ones; the tier lists only models that fit all of them.
  • Base M1 Macs (8 and 16 GB) have their own tiers. Their bandwidth is so low that they get different picks from other Macs with the same memory.
  • The Latitude 7350, Pro 14 Premium and Pro Max 16 have no discrete GPU, or only a 6-8 GB one. Their RAM bandwidth is about 90-137 GB/s, versus 150-614 on Pro/Max Macs.
    • Only MoE models reach usable speed on them. MoE (mixture of experts) means only a few billion parameters are read for each token.
    • Bandwidth figures: Apple specs [23]; NVIDIA [24]; Dell RAM speeds [25], with bandwidth computed as MT/s × 16 bytes, i.e. a 128-bit bus (estimate). Dell's manuals give the memory bus width as 64-bit; the report reads that as per channel, with two channels (unsourced). If the total bus is 64-bit, every Dell speed estimate that runs from system RAM halves. The base M1's ~67 GB/s isn't published by Apple; it's derived from Apple's "M2 has 50% more" (unsourced).
  • The Pro Max 16 Plus tiers depend on the GPU.
    • A model runs entirely in VRAM if it's no bigger than VRAM minus 3 GB; for coding, its 64k context must also fit in VRAM. Only the 24 GB RTX PRO 5000 can hold a 27B dense model that way.
    • Windows and Dell RAM: a model run from system RAM must fit in RAM minus 10 GB (estimate); for coding, that includes 64k of context.
    • Otherwise Ollama splits the model between the GPU and system RAM, and RAM speed sets the pace.

MLX builds take the same fix. Ollama passes num_ctx to the MLX runner, which reports it as the model's context length [43]. qwen3.8-flash-next:125b-a6b-nvfp4 ships num_ctx 262144 [7]; the Modelfile value replaces it, and OpenCode's limit.context must match whichever applies (section 5).

Sampling settings: most Ollama tags already carry the vendor's recommended values. For example, qwen3.8 ships with temperature 1, top_p 0.95 and top_k 20, matching its model card [34].

qwen3.6:35b-a3b for coding. Both its builds (-nvfp4 and -q4_K_M) ship presence_penalty 1.5 [7], Qwen's value for general tasks in thinking mode, which it runs by default. 3. Mac GPU memory limit

macOS caps how much unified memory the GPU can use. The default cap isn't published by Apple; it's commonly reported as about 2/3 of RAM on Macs up to 36 GB and about 3/4 above that (unsourced). A model that doesn't fit under the cap still runs, but part of it runs on the CPU (unsourced). ollama ps shows that split [41], and Ollama advises avoiding CPU offload for best performance [14].

Check first. Load the model, then run ollama ps. If PROCESSOR reads 100% GPU, the model is entirely on the GPU, so leave the cap alone. A split such as 48%/52% CPU/GPU means part of it spilled [41].

Tier When to raise the cap Example value
Macs up to 36 GB When a coding pick's weights plus 64k of context exceed the default cap: the coding fit estimates, and the General context sizes in section 2, allow up to about 80% of RAM 6500 on 8 GB · 13000 on 16 GB · 14700 on 18 GB · 19600 on 24 GB · 26000 on 32 GB · 29000 on 36 GB
Mac 128 GB Required for qwen3.8-flash-next (105 GB), the #1 pick. Check ollama ps with the coding build nemotron-3.5-super:120b-a12b-q4_K_M (90 GB, close to the default cap); the General build 120b-a12b-nvfp4 (80 GB) and the coding pick ornith-1.5:122b-nvfp4 (73 GB) fit under it (estimate) 114000
Mac 48-96 GB Not needed for the picks in this report —

The value is in MB. It must be larger than the model and smaller than total RAM [48]. The example values leave about 1.6-17 GB for macOS (estimate). On 8 and 16 GB Macs that's tight: close other apps while a model is loaded, and watch for swapping.

Until the next reboot:

sudo sysctl -w iogpu.wired_limit_mb=26000

Permanent: add the same setting to /etc/sysctl.conf, which macOS applies at boot (unsourced):

echo "iogpu.wired_limit_mb=26000" | sudo tee -a /etc/sysctl.conf
  • Risk: setting it too high starves macOS of memory, which causes swapping or freezes (unsourced). Raise it in small steps and re-check ollama ps.
  • To undo: set it to 0, which is commonly reported to restore the macOS default (unsourced), and remove the line from /etc/sysctl.conf.

4. Tag choice

  • Ollama 0.40 runs supported models on MLX by default on Apple silicon, starting with Qwen 3.8, Qwen 3.6, Qwen 3.5 and Gemma 4 [4]. MLX is Apple's machine-learning framework [3]. MLX builds run only on Apple silicon; Windows uses GGUF.
  • How the Mac tables pick a build: of the builds that fit the tier and pass the speed filter, the one with the highest estimate. An MLX build within 10% of that is listed instead, unless it would lose 15 tok/s on a machine where the faster build has it. Among MLX builds, -nvfp4 comes first: Ollama says NVFP4 keeps model accuracy while cutting memory use [3]. -int4 is listed only when it's more than 10% faster, as for qwen3.5:27b-int4.
  • Why near-ties go to MLX: Ollama reports NVFP4 generating about 20% faster than q4_K_M [5], and MLX is Ollama's default on Macs [4]. The speed estimates don't include that gain, because it isn't measured on these machines.
  • Many short tags hold two builds. For example, qwen3.8:27b, qwen3.6:27b, qwen3.6:35b-a3b, qwen3.5:9b, gemma4:12b, gemma4:26b and nemotron-3.5-super:120b-a12b each list an MLX build and a GGUF build [7]. On Apple silicon Ollama picks MLX first; elsewhere it picks GGUF first [49]. The tables always give the full tag.
  • flint and flint:40b also hold two builds, but the GGUF one needs Ollama 0.40.9, which is only a release candidate as of 2026-10-22 [7][50]. On a Mac, use flint:40b-a2b-qat-int4. Ollama 0.40.8's notes say Flint runs on macOS only for now [2].
  • To check which engine loaded, run ollama ps: its RUNNER column reads mlx for the MLX build [51].
  • If an MLX build misbehaves, switch to the GGUF build of the same model (listed beside it in the Model reference). It has the same score; the estimates differ by 10% or less, except for nemotron-3.5-super (the MLX build is 12% smaller), nemotron-3.5-lightning (the MLX build is 24% smaller, and the GGUF build doesn't fit 32 GB Macs for General use) and qwen3.8-flash-next (no GGUF build fits). flint has no GGUF build that runs on Ollama 0.40.8. Open MLX reports, none confirmed by Ollama:
    • #18754: the GPU only 50-70% busy on an M4 Pro (0.40). If MLX isn't faster on your Mac, use GGUF.
    • #16279: tool-call arguments arrive in one piece at the end instead of streaming, so a long file write can hit a client timeout. The report says non-MLX backends stream tool calls properly.
    • #18131: MLX's prompt cache pushing a 32 GB Mac into heavy swap during agent sessions.
  • Ollama 0.40.4 fixed two MLX bugs [2]: the per-tool-call memory leak (#18620, PR 18955) and the "Maximum threads" crash on qwen3.6:35b-mlx and qwen3.8:27b-mlx (#18846, PR 18956). Ollama 0.40.5 and 0.40.7 update MLX again [2]. Use 0.40.8 or later; Flint's MLX build requires it [7].
  • ollama show <tag> now reports the model's parser and renderer (since 0.40.7) [2]. Use it to see whether a model you pulled shares a parser with a ⚠ flag in this report.

5. OpenCode 2.x (~/.config/opencode/opencode.jsonc)

Ollama is discovered automatically. OpenCode 2 probes http://127.0.0.1:11434, lists every Ollama model that can chat, and reads context, vision and tool-use capabilities from Ollama, with no provider config needed [52]. Select a model as ollama/<tag>.

Still override the context limit. Discovery reads each model's maximum context from Ollama, not your num_ctx [53], and requests go through Ollama's /v1 endpoint, which has no way to set the context size [54][16]. So keep the Modelfile fix from section 2, and tell OpenCode the same limit. A limit set in config overrides the discovered value [55]. Example for a Mac with 48-96 GB, matching the Modelfile above [54][52]:

{
  "$schema": "https://opencode.ai/config.json",
  "model": "ollama/oc-qwen3.8-27b",
  "providers": {
    "ollama": {
      "models": {
        "oc-qwen3.8-27b": {
          "name": "Qwen3.8 27B (local, 128k)",
          "capabilities": { "tools": true, "input": ["text", "image"], "output": ["text"] },
          "limit": { "context": 131072, "output": 16384 },
        },
      },
    },
  },
  "compaction": { "auto": true },
}
  • limit.context must equal the model's num_ctx. It tells OpenCode when to compact; it doesn't change Ollama. Automatic compaction is on by default and, since OpenCode 2.1.0, keeps 15% of the limit free (up from 10%), at least 16k tokens [56][57]. Below a limit of about 107k the 16k minimum applies, so at 64k nothing changes; at 128k about 19.7k is kept free instead of 16k.
  • OpenCode 2.1 can't be downgraded cleanly. Sessions compacted by 2.1 can't be loaded by 2.0 [58].
  • Malformed tool calls fail visibly (since 2.0.25). OpenCode no longer repairs bad tool-call JSON; it sends the model a tool error so it can retry [59]. With the parser bugs above, expect the odd retried tool call rather than a silent fix.
  • Key names changed from 1.x: 2.x uses providers, package, settings and capabilities.tools [54][52], where 1.x used provider, npm, options and tool_call [60]. small_model isn't in the 2.x docs; title and summary work is done by hidden built-in agents [61].
  • The config schema describes 2.x. The schema at opencode.ai/config.json has the providers key and marks 1.x keys such as provider and small_model as deprecated [60].
  • Remote Ollama: set providers.ollama.settings.baseURL to its /v1 URL [52].
  • Keep MCP servers to a minimum. MCP tools consume model context [62], on top of OpenCode's own system prompt and tools.
  • Prefer the config above to ollama launch opencode. Ollama's OpenCode page shows only 1.x setup (the Windows install is the 1.x package opencode-ai; the manual config uses provider and npm), and it doesn't say which OpenCode version ollama launch targets [15]. An open report says the config ollama launch opencode writes uses the model's maximum context rather than your num_ctx, so compaction starts too late (#19172).
